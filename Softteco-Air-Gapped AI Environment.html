Constraints

What is off the table

Three hard prohibitions shape everything that follows. None of them can be handled with a configuration flag — only with architecture.

  • RULE 1

    No external APIs

    Claude, GPT, and Gemini are excluded as a category. Inference must run locally, with the right to operate offline and indefinitely without contacting a vendor.

  • RULE 2

    No models of Chinese origin

    Qwen, DeepSeek, GLM, and Kimi are excluded regardless of license or benchmark position. This removes most of the top of the open-weight leaderboards.

  • RULE 3

    No outbound traffic from the working tool

    The agent reads the filesystem and executes commands. Any outbound channel is an exfiltration channel. This is why we fork rather than install upstream.

What remains: open-weight models originating in the United States and the European Union. Three candidates are practically viable.

Architecture

OpenWork fork → vLLM

OpenWork is an Electron shell around the OpenCode agent. OpenCode talks to any OpenAI-compatible endpoint, so swapping a cloud model for local vLLM is one line of configuration. The real work is elsewhere: removing everything that reaches outward.

The organizational controls that Den provides — desktop policies, distributing skills and plugins, pinning app versions — are reproduced inside the perimeter: a skills registry on internal Git, policies pushed through the existing MDM, app versions served from the internal package repository.

The perimeter is enforced at the network layer: egress deny-all by default, with the internal vLLM address as the only exception. Even if a forgotten call survives somewhere in the dependency tree, it goes nowhere.

Risk register · Platform

Risks of forking OpenWork

Forking solves the main problem and introduces its own. Everything below is disclosed before signature rather than after.

CriticalR-01

Mixed licensing in the repository

The project tree contains an ee/ directory — enterprise edition. Part of the codebase is almost certainly not under a permissive license, and the right to fork some functionality may not exist.

MitigationLegal review of the LICENSE file and the ee/ directory before work begins. The build excludes ee/ entirely. Any ambiguous wording goes to the rights holder in writing.
CriticalR-02

The agent executes commands and writes to disk

This is not a chatbot. OpenCode spawns processes, edits files, and operates on repositories. A model error or a compromised skill becomes an action on the workstation.

MitigationMandatory approval for privileged operations, execution inside an isolated filesystem sandbox, and an append-only audit log of agent actions forwarded to the client's SIEM.
CriticalR-03

Skills, plugins, and MCP as an attack surface

OpenWork is designed around marketplaces of installable modules. Inside a closed environment, any third-party module is executable code of unknown provenance behind the perimeter.

MitigationMarketplaces disabled at build time. Internal registry only, with code review and signing. The list of permitted MCP endpoints is hard-coded in configuration.
HighR-04

npm supply chain

The project runs on pnpm, Electron, and a Rust toolchain, with over four thousand commits and thousands of transitive dependencies. A textbook supply-chain surface.

MitigationInternal registry mirror, pinned lockfile, SBOM generated on every build, vulnerability scanning, and reproducible builds.
HighR-05

Electron auto-update

Upstream publishes separate updater manifests for its public, cloud, and enterprise builds. A live update channel inside a protected environment is unacceptable. Separately, upstream notes its Windows installer is temporarily unsigned.

MitigationUpdater stripped from the build. Distribution through the internal repository only, signed with the client's certificate, with hash verification at install time.
HighR-06

Drift from upstream

Upstream ships releases almost daily. Without a synchronization policy, within six months the fork becomes an unmaintained branch with no security fixes.

MitigationQuarterly rebase onto the upstream release branch, an automated regression suite, and a dedicated diff review for new network calls before every merge.
HighR-07

Moving model weights into the environment

Weights run to hundreds of gigabytes hosted externally. For Inkling that is roughly 670 GB in NVFP4, or about two terabytes for BF16.

MitigationDownload in a staging zone, checksum verification against published hashes, antivirus and structural validation of safetensors, then transfer through a one-way gateway.
HighR-08

--trust-remote-code requirement

The official vLLM recipe for Inkling requires this flag — meaning arbitrary Python shipped inside the model checkpoint is executed at load time.

MitigationManual audit of the checkpoint's modeling code, inference confined to a separate container with no network access and no access to client data, and a pinned checkpoint revision.
MediumR-09

No vendor accountability

Open-weight models ship as-is. No lab carries obligations for quality, output safety, or fix timelines. Inkling's authors explicitly recommend layering your own moderation on user-facing deployments.

MitigationSoftTeco Group carries the SLA, not the lab. Own output-filtering layer, an acceptance test suite built on the client's domain tasks, and a migration path to an alternative model that does not require rewriting the integration.
MediumR-10

Dependence on pre-release vLLM builds

Some accelerations exist only in nightly — MTP speculative decoding for Gemma 4, for example, has not landed in a stable release.

MitigationProduction runs a pinned stable vLLM version only. Nightly optimizations are adopted as a separate stage after a regression run.

The headline finding. Gemma 4 31B lands within a single point of Mistral Medium 3.5 while requiring a quarter of the VRAM and carrying no license carve-out. Option C in its Medium 3.5 form is not economically defensible next to option B.
Where the gap is wider than the scale suggests. On static knowledge tests Gemma 4 31B looks near-level with the leaders. The gap to Inkling opens up in long agentic chains: Inkling scores 1238 Elo on GDPval-AA v2 while averaging 25K output tokens per task, roughly half the spend of its nearest rivals. For an OpenWork deployment, that is precisely the metric that decides practical usability.

Index figures are drawn from publications across several months and methodology revisions (v4.0 through v4.1.1). A 1–2 point difference between closely ranked models sits inside the margin of comparison and should not drive the decision on its own.

Recommendation

Two tiers instead
of one choice

Treating A, B, and C as mutually exclusive is the wrong framing. Options A and B solve different problems and pair well. Option C fills neither role: four times the cost of B, one index point ahead, and a license carve-out attached.

Tier 1 · Volume

Gemma 4 31B

$90–110K

Two servers, 2 × RTX PRO 6000 each. Covers the bulk of everyday OpenWork tasks: document work, code, image and scan analysis. Installs into a standard rack in one to two weeks with no changes to power or cooling.

Tier 2 · Heavy

Inkling 975B

$1.3–1.8M

A B300 node for deep analysis, long agent runs across large codebases, million-token context, and audio processing. Added in a second phase, once tier 1 is in service and there is measured data on the tasks it cannot carry.

Routing between tiers runs in a proxy ahead of OpenCode: a rule on task type and context length, switching transparently for the user. The integration surface stays singular — an OpenAI-compatible endpoint — so replacing or adding a model requires no change to the OpenWork fork.

Why this works commercially: the client does not need to defend a $1.8M budget line to get a working tool. Tier 1 goes live this quarter and produces the measured results that justify tier 2.
